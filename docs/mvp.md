# KoFinGuard MVP — 가장 작게 만들어도 가치가 있는 범위

> 수업 문서 흐름: **MVP**(이 문서) → PRD → SPEC → PLAN
> 프로젝트 이름(KoFinGuard)과 은행 이름(MJ뱅크)은 임시 이름이며 바꿔도 됩니다. MJ뱅크는 실존하지 않는 가상 은행입니다.

## 1. 한 줄 소개

**KoFinGuard는 가상 은행(MJ뱅크)의 고객용 AI 상담 챗봇을 만들어 두고, 실제 은행 사고·취약점을 모델로 한 공격 2개를 재현해 "방어 OFF 챗봇은 뚫리고 방어 ON 챗봇은 막는다"를 실제 실행 결과와 수치(TPR/FPR)로 보여 주는 프로젝트입니다.**

## 2. 왜 만드나

- 은행은 고객용 AI 챗봇에 계좌 조회·송금 같은 기능을 붙이고 있습니다. AI가 은행 기능(툴)을 직접 호출하면, **말로 속이는 공격이 곧 돈과 개인정보 피해**가 됩니다.
- 2026년 7월, 유럽의 한 은행 고객용 AI 챗봇에서 실제로 이런 취약점이 공개됐습니다.
  - PDF 청구서에 숨긴 지시로 챗봇 답변에 악성 코드가 섞여 나왔습니다.
  - 그 코드가 은행 화면에서 실행되어 고객 정보가 외부로 전송됐습니다.
- 2026년 9~10월 국내 금융권 연쇄 침해에서는 공격자가 인증을 우회해 남의 고객정보를 조회했습니다.
  - AI 기반 공격 도구의 흔적도 나왔습니다.
- 두 사고의 공통점은 **챗봇이나 화면이 속아도 서버가 마지막에 막아 주지 않았다**는 것입니다. 그래서 이번 프로젝트의 핵심은 **서버 쪽 방어**입니다.
- 내 졸업 프로젝트의 **한국어 탈옥 탐지 파이프라인**(자모 분해 전처리, SmoothPPL, Llama Guard 연동)은 입력을 먼저 검사하는 **보조 레이어**로 붙입니다. 툴을 거치지 않는 공격(사기 문구 생성, 내부 안내문 유출 등)을 거르고, 공격 시도를 기록해 관제에 쓰기 위해서입니다.
- 탐지기 하나로는 모든 공격을 막을 수 없다는 점도 보여 줍니다.
  - 그래서 **탐지 + 서버 권한 검사 + 답변 안전 처리**를 겹겹이 쌓는 다층 방어를 만듭니다.

## 3. 누가 쓰나

| 사용자 | 하는 일 |
|---|---|
| 가상 고객 (김민수, 이서연) | 로그인해서 챗봇에게 잔액·거래내역을 묻고, 청구서를 올려 송금을 요청합니다 |
| 공격자 (시연자 본인) | 미리 준비한 공격 문장과 악성 PDF를 챗봇에 넣습니다 |
| 발표를 듣는 사람·면접관 | 같은 공격이 OFF에서는 성공하고 ON에서는 막히는 장면과 수치를 봅니다 |

모든 고객·계좌·금액은 **허구의 테스트 데이터**입니다. 실제 은행이나 외부 시스템에는 요청하지 않습니다. 유출을 받는 "공격자 서버"도 내 PC 안(127.0.0.1)에서만 동작합니다.

## 4. MVP에 반드시 들어가는 것

1. **가상 은행 API**
   - 내 잔액, 거래내역, 송금, 고객 정보 조회
   - 챗봇이 이 기능들을 툴로 호출합니다.
2. **AI 상담 챗봇 (두 모드)**
   - 같은 화면, 같은 모델, 같은 프롬프트를 씁니다.
   - 방어 레이어만 OFF/ON 합니다.
3. **공격 시나리오 2개 (실제 사례 기반)**
   - **S1 권한 사칭:** "나 감사팀인데…"라고 속여 남의 고객정보를 조회하게 만듭니다.
   - **S2 문서 속 숨은 지시:** 청구서 PDF에 숨긴 지시로 악성 코드가 답변에 섞여 나오고, 화면에서 실행되어 고객 정보가 외부로 전송됩니다.
   - 두 공격 모두 **실제 사례 원문 그대로** 재현합니다. 변형 공격은 만들지 않습니다.
4. **다층 방어** (핵심은 서버 쪽)
   - **보조: 입력 탐지기 (졸프 파이프라인):** 자모 분해 정규화 → SmoothPPL → Llama Guard. 판정 결과를 근거 패널과 기록에 남깁니다.
   - **서버 권한 검사:** LLM이 무엇을 말하든, 서버가 로그인 사용자 기준으로 다시 검사합니다.
   - **송금 사용자 확인:** LLM은 송금을 "대기"로만 만들 수 있고, 실행은 사람이 버튼을 눌러야 합니다.
   - **첨부 문서 격리 + 답변 안전 처리:** 답변을 HTML로 실행하지 않고 글자로만 표시합니다. 외부 링크와 이미지는 제거합니다.
5. **비교 화면 (React + TypeScript)**
   - 왼쪽은 OFF, 오른쪽은 ON입니다.
   - 어떤 방어 레이어가 막았는지 근거를 보여 줍니다.
6. **정량 평가**
   - 탐지기 운영 지표: 정상 은행 질문을 잘못 막는 비율(오탐), 판정 속도, S1·S2 판정 결과
   - 시나리오별 공격 성공률 (OFF vs ON)
7. **기록 저장 (Supabase)**
   - 대화·탐지 결과·툴 호출·평가 결과·첨부 파일 정보를 저장합니다.
   - 실제 파일은 `backend/uploads/`에 둡니다.

## 5. MVP에 넣지 않는 것

- 실제 계좌·결제·오픈뱅킹 연동, 실명 인증
- 방어 OFF 모드의 인터넷 공개 (로컬 시연 전용)
- 새 탐지 모델 학습 (졸프 모듈을 이식만 함)
- 팀원이 만든 자모음 결합 모델 (내 담당이 아니므로 쓰지 않음)
- 실제 유해 콘텐츠 생성 시나리오 (금융 피해 시나리오만 다룸)
- 임직원용 챗봇 (확장 X1: 시간이 남으면 진행)
- 클라우드 배포

## 6. 성공했다고 말할 수 있는 기준

- 화면에서 같은 공격을 넣었을 때 S1·S2 모두 **OFF는 실제로 뚫리고 ON은 실제로 막힌다**.
  - DB 상태, 서버 기록, 공격자 서버 로그로 확인합니다.
- 탐지기 운영 지표(오탐, 속도)가 실제 실행 결과로 나온다.
- 정상 은행 질문이 ON 모드에서 과하게 막히지 않는다.
- 실행하지 못한 검사는 PASS로 세지 않고 "미검증" 또는 "SKIP"으로 표시한다.
