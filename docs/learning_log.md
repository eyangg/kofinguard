## 2026-10-30 · Phase 0 (환경 준비)

**겪은 문제**

Q. `ollama` 명령을 찾을 수 없다고 나온다.
A. Ollama가 설치되지 않았거나, 설치 직후라 열려 있던 터미널이 바뀐 PATH를 모르는 것이다. 설치 후 터미널(또는 VS Code)을 새로 연다.

Q. `ollama launch claude`를 쳤더니 모델을 고르라고 나온다.
A. Claude Code를 Ollama 모델로 실행하는 명령이라 이 프로젝트와 상관없다. Esc로 나가고 `ollama pull llama-guard3:8b`처럼 필요한 모델만 받는다.

Q. Qwen 파일이 0MB이고 내용이 `Entry not found`다.
A. 다운로드 주소가 틀려서 오류 문구가 파일로 저장된 것이다. 지우고 정확한 주소로 다시 받는다. 정상 크기는 2,104,932,768바이트다.

Q. 졸프 코드 중 무엇을 가져오나? 자모음 결합 RNN도 필요한가?
A. RNN(팀원 담당)은 안 쓴다. SmoothPPL은 Qwen 노트북이 최종본이다(Llama-3.1-8B는 폐기). `SmoothPPL_4_20`은 Llama-3.1로 잰 버전이라 그 안의 수치는 근거로 쓰지 않고, 120문장 평가 데이터만 쓸 수 있다.

Q. 왜 GitHub 저장소를 비공개로 하나?
A. 실제로 통하는 공격 문장과 공격자 서버 코드가 들어가고, 졸프 자료는 팀 작업이며, 키가 실수로 올라가면 공개 저장소에서는 바로 도용된다. 다 만든 뒤에 공개로 바꿔도 된다.

## 2026-10-30 · Phase 1 (프로젝트 뼈대)

**이해한 것**

Q1. 왜 프론트는 `/api`만 부르고, Vite가 8000으로 넘겨 주나?
A. 화면(5173)과 백엔드(8000)는 포트가 달라서 브라우저가 다른 사이트로 보고 요청을 막는다(CORS). 그래서 화면은 같은 주소의 `/api`만 부르고 Vite가 뒤에서 8000으로 전달한다. 브라우저는 백엔드 한 곳만 알게 되니까 DB 비밀번호와 API 키는 백엔드 안에만 있고, 권한 검사도 서버가 하게 된다.

Q2. 왜 `.env`는 Git에서 빼고 `.env.example`만 올리나?
A. `.env`에는 OpenAI 키와 DB 비밀번호 같은 진짜 비밀값이 있고, 한 번 GitHub에 올라가면 지워도 커밋 기록에 남아 도용될 수 있다. `.env.example`은 항목 이름과 설명만 있는 안내서라서, 다른 PC에서도 무엇을 채워야 하는지 알 수 있다. 그래서 `.gitignore`로 `.env`만 막고 `.env.example`은 허용한다.

Q3. 왜 기본 pytest는 모델이나 OpenAI 없이 돌아야 하나?
A. 실제 AI를 부르면 돈이 들고, 느리고, 매번 답이 달라서 테스트 결과가 들쭉날쭉해진다. 가짜 LLM은 항상 똑같이 움직이니까 내 코드가 맞는지만 빠르게 확인할 수 있고, 인터넷이나 키가 없는 곳에서도 돌아간다. 실제 모델 검사는 `-m models`나 `-m llm`으로 따로 표시해 두고 필요할 때만 돌린다.

**겪은 문제**

Q. `.env.example`이 없어서 키를 어디에 넣을지 몰랐다.
A. `.env.example`은 Phase 1에서 생긴다. 그 전에는 `backend\.env`를 직접 만들어 `OPENAI_API_KEY=...`만 넣으면 된다.

Q. `npm run dev`가 "스크립트를 실행할 수 없으므로 npm.ps1을 로드할 수 없습니다"로 막힌다.
A. PowerShell 보안 설정이 `.ps1` 실행을 막는 것이다. `npm.cmd run dev`로 실행하거나 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`를 한 번 실행한다.

## 2026-10-30 · Phase 2 (테이블과 시드 데이터)

**이해한 것**

Q1. 왜 테이블을 직접 만들지 않고 Alembic 명령으로 만드나?
A. 테이블 구조를 코드(마이그레이션 파일)로 남겨 두면, 내 PC의 SQLite든 나중의 Supabase든 명령 하나(`upgrade head`)로 똑같이 만들 수 있다. 이미 적용한 변경은 `alembic_version`에 기록돼서 다시 실행해도 중복으로 만들지 않는다.

Q2. 왜 `DATABASE_URL`이 없으면 SQLite로 넘어가지 않고 멈추나?
A. 설정이 빠졌는데 몰래 SQLite로 넘어가면, Supabase에 저장되는 줄 알았던 시연 데이터가 실제로는 내 PC 파일에만 쌓이는 사고가 난다. 멈추고 무엇을 확인할지 알려 주는 게 더 안전하다.

Q3. 왜 비밀번호를 원문이 아니라 해시로 저장하나?
A. 해시는 되돌릴 수 없는 변환이라 DB가 유출돼도 원래 비밀번호를 알 수 없다. 로그인할 때는 입력한 비밀번호를 같은 방식으로 해시해서 저장된 값과 비교만 한다. 사람마다 다른 소금값(salt)을 섞어서 같은 비밀번호라도 저장값이 달라진다.

**겪은 문제**

Q. Supabase에 예전 BankGuard 데이터가 보여서 헷갈린다.
A. Phase 2~7은 내 PC의 `backend\kofinguard.db`(SQLite) 파일만 쓴다. Supabase에는 아직 아무것도 연결하지 않았으니 거기 보이는 건 전부 BankGuard 데이터다. Phase 8에서 BankGuard에 같은 이름의 테이블(`customers` 등)이 있는지 먼저 확인한다.

Q. 서버가 어느 DB를 쓰는지 어떻게 확인하나?
A. 서버를 켠 터미널 로그에 `INFO: DB 연결: sqlite (kofinguard.db)` 줄이 나온다. 브라우저(http://127.0.0.1:5173)를 새로 고칠 때마다 `GET /api/health ... 200 OK` 줄이 생기면 화면 → 프론트 → 백엔드 연결이 정상이다. DB 내용은 VS Code의 SQLite Viewer 확장으로 `kofinguard.db`를 열어 본다.

## 2026-10-30 · Phase 3 (로그인·로그아웃)

**이해한 것**

Q1. 로그인 상태를 왜 httpOnly 쿠키로 유지하나?
A. httpOnly 쿠키는 브라우저가 요청마다 자동으로 보내지만, 화면의 자바스크립트는 읽을 수 없다. 그래서 S2처럼 화면에 악성 코드가 실행돼도 로그인 쿠키 자체를 훔쳐 가지는 못한다. `SameSite=lax`는 다른 사이트에서 몰래 보내는 요청에 쿠키가 붙는 걸 줄인다.

Q2. 쿠키에 사용자 정보를 넣지 않고 "무작위 세션 ID + 서명"만 넣는 이유는?
A. 쿠키에 고객번호를 그대로 넣으면 사용자가 값을 바꿔 남의 계정인 척할 수 있다. 무작위 ID는 추측할 수 없고, `KFG_SESSION_SECRET`으로 만든 서명이 있어 조작하면 바로 401이 된다. 누가 로그인했는지는 서버 메모리에 두기 때문에, 로그아웃하면 서버에서 지워서 예전 쿠키를 다시 보내도 401이 된다. 대신 서버를 다시 켜면 모두 로그아웃된다.

Q3. 틀린 아이디와 틀린 비밀번호에 왜 같은 문구를 쓰나?
A. "없는 아이디입니다"처럼 구분해 주면 공격자가 어떤 아이디가 존재하는지 알아낼 수 있다. 그래서 문구도 같게 하고, 없는 아이디일 때도 비밀번호 검사를 똑같이 해서 응답 시간으로도 구분할 수 없게 했다.

**겪은 문제**

Q. 코드를 바꾼 뒤 서버를 다시 켰더니 시작하지 않는다.
A. `.env`에 `KFG_SESSION_SECRET`이 없어서다. backend 폴더에서 `.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(32))"`로 값을 만들어 `.env`에 넣는다. 값은 채팅에 붙이지 않는다.

Q. 로그인을 화면 없이 어떻게 확인하나?
A. http://127.0.0.1:8000/docs (Swagger)에서 `POST /api/auth/login` → Try it out → `{"login_id": "minsu", "password": "demo1234!"}` → Execute. 그다음 `GET /api/me`가 200이면 로그인된 것이다. 로그아웃 후 다시 `/api/me`를 부르면 401이 나온다.

## 2026-10-30 · Phase 4 (가상 은행 기능)

**이해한 것**

Q1. 송금에서 "출금·입금·기록을 한 번에 처리한다"는 게 왜 중요한가?
A. 내 계좌에서 돈을 뺀 직후 오류가 나서 상대 계좌 입금이나 거래 기록이 빠지면 돈이 사라진다. 그래서 세 작업을 하나의 DB 트랜잭션으로 묶고, 중간에 하나라도 실패하면 rollback으로 전부 원래대로 돌린다. 테스트에서 기록 단계를 일부러 고장 내서 잔액이 그대로인지 확인했다.

Q2. 하루 한도와 잔액 검사를 왜 챗봇 안내문이 아니라 서버 코드가 하나?
A. 챗봇은 말로 속일 수 있어서 "한도 무시해"라는 공격에 넘어갈 수 있다. 서버 코드는 챗봇이 뭐라고 하든 같은 규칙을 지킨다. 그래서 금액·잔액·한도 검사는 OFF/ON 모두 서버가 한다. OFF와 ON의 차이는 "남의 고객번호를 그대로 쓰는지"(S1)와 "바로 송금하는지, 사람이 [확인]을 눌러야 하는지"다.

Q3. [확인] 기능은 왜 챗봇 툴이 아니라 사람이 누르는 API로만 있나?
A. 챗봇이 확인까지 할 수 있으면 공격 문장 하나로 송금이 끝까지 실행된다. 확인을 사람 버튼으로만 두면 챗봇이 속아도 "송금 대기"까지만 만들 수 있다. 대기 건은 5분이 지나면 만료되고, 남의 대기 건은 "찾을 수 없습니다"(404)로 답해서 존재 여부도 알려 주지 않는다.

**알아 둘 것**
- 금액은 원 단위 정수만 받는다. 챗봇이 `1.5`, `"100"`, `true`처럼 이상한 값을 넘겨도 거절한다.
- "하루"는 한국 시간 0시 기준이고, 실제로 나간 금액만 한도에 들어간다. 송금 대기는 한도에 안 들어가고, 확인하는 순간 다시 검사한다.
- 받는 계좌가 MJ뱅크 계좌면 입금되고, 외부 계좌(예: MJ전자)면 출금만 된다.
